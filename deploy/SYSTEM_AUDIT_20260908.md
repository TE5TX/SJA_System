### F01：传递依赖安全债务

- 证据：`SJA_Sys_Java/pom.xml` 的 EasyExcel 与验证码依赖；本次 `mvn dependency:tree` 的实际解析结果。
- `poi-ooxml:5.2.5` 命中 CVE-2025-31672 的影响范围。官方说明 5.4.0 起拒绝 OOXML ZIP 中重复名称条目，避免不同读取工具解析出不同内容。本系统 `UserImportService.readWorkbook`（约 167 行）通过 EasyExcel 读取上传表格，存在相关解析入口，但本次没有投递恶意工作簿。[Apache POI 官方公告](https://poi.apache.org/)
- `commons-compress:1.25.0` 命中 CVE-2024-25710、CVE-2024-26308 的版本范围；1.26.0 修复。两者分别涉及 DUMP、Pack200，**不能因为系统读取 XLSX 就直接认定可触发这两个漏洞**，本次未找到应用主动解析这些格式的路径。[Commons Compress 官方公告](https://commons.apache.org/proper/commons-compress/security.html)
- `commons-lang3:3.17.0` 命中 CVE-2025-48924，修复下限 3.18.0；涉及特定类解析长输入，本次未确认外部输入能否到达触发方法。[Apache 官方问题记录](https://issues.apache.org/jira/browse/CONFIGURATION-853)
- 未把 `commons-io:2.15.0` 误报为 CVE-2024-47554：官方影响范围是低于 2.14.0。[Commons IO 官方公告](https://commons.apache.org/proper/commons-io/security.html)
- 建议：统一管理传递依赖，升级到兼容且已修复的稳定版本；POI 系列版本保持一致。上述是对应漏洞修复下限，不是“升级到这个最低版本就永久安全”。补完整 SCA/SBOM、镜像扫描和导入导出兼容测试。
- 验收：解析后的依赖树不再包含这些受影响版本；六种稿费导出与人员导入回归通过；畸形文件在隔离测试环境被安全拒绝。

### F02：重复计费校验存在竞争窗口

- 证据：`FeeServiceImpl.submitFee` 约 83–145 行、`ensureNotDuplicate` 约 1652 行、`hasDuplicateSubsidy`；基线 `sql/sja_system_db_202608131609.sql`。
- 两个独立任务能在对方提交之前都通过 `selectCount`，随后写入同一作品或同月同类人员补贴。普通事务不自动把该业务条件变成互斥条件。
- 当前 `biz_work_contributor` 有 `(work_type, work_id, user_id, role_in_work)` 唯一索引，这是已有保护；但两个任务拥有不同 `work_id`，该索引不能阻止跨任务重复计费。异步执行标记只能防同一 taskId 的重复执行。
- 建议：设计业务幂等标识及数据库唯一约束；补贴可用“月份+类别+人员”额度明细约束，作品先定义链接/标题/平台/日期的规范化身份；明确软删除后的重提规则。不要在未经清理历史重复数据时直接加约束。
- 验收：测试库中用两个不同幂等键并发提交同一业务对象，只成功一次，另一请求得到明确冲突；回滚不遗留半成品。

### F03：入队过程中状态不一致

- 证据：`AsyncTaskQueueService.enqueue` 约 79–159 行；`writeStatus`、`append`、`accepted`、`cleanupActiveKey`。
- 幂等键 SETNX、状态 HSET/EXPIRE、Stream XADD、受理结果读取是多次独立调用。尤其 XADD 成功后，读取受理状态失败仍进入 RuntimeException 分支，删除状态和幂等键，而消息可能已经被消费。
- 结果可能是页面报失败但后台写入成功、状态查询 404、再次提交成为新任务。容量检测也不是原子操作，多请求可能一起越过上限。
- 建议：将 Redis 侧受理步骤放入经过校验的原子脚本，或采用数据库任务表/outbox 作为事实来源。对“结果未知”按同一幂等键查询，不直接视为完全未入队；活动键清理使用比较后删除脚本。
- 验收：逐个注入状态写入、XADD、受理结果读取失败，要求同一请求最终只有一个可查询的结果，且没有状态被清除但仍执行的孤立任务。

### F04：头像 API 被 Nginx 图片规则截走

- 证据：`SJA_Sys_Vite/nginx.conf:9,24`；`deploy/nginx.https.conf.template:25,40`。
- 普通 `location /api/` 后还有匹配 `.jpg/.png` 的正则 location。头像 URL 本身以图片后缀结束，会进入静态 `try_files ... =404` 而非后端。该推断符合 Nginx 的 location 匹配规则。[Nginx 官方说明](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)
- 这能解释“头像返回 404”，但**404 本身不证明匿名鉴权正确或错误**；本次没有检查服务器实际加载的配置。
- 建议：API 前缀采用 `location ^~ /api/`，或把静态缓存限定在资产目录。不要通过开放匿名头像访问绕过路由错误。
- 验收：经过 Nginx，对真实已绑定头像，匿名返回 401、授权返回 200；不存在的头像在授权后返回 404；API 响应不能带静态资源的 public immutable 缓存策略。

### F05：头像文件生命周期不完整

- 证据：`UploadController.uploadAvatar`、`AvatarStorageService.store`、`validateAssignableAvatar`、`deleteAfterCommit/deleteAfterRollback`。
- 已有 5MB、尺寸/像素上限、内容解码重编码、路径校验，这是正确保护。但登录用户可以反复调用独立上传接口而不保存个人资料。每次产生新 UUID 文件，现有旧头像替换/回滚清理覆盖不到这些未绑定文件；未找到暂存过期清理或每账号累计配额。
- 暂存文件也没有绑定上传者身份，分配时只验证“文件存在、没有被别人引用”，而非“由当前用户上传”。UUID 降低猜测可能性，但不是所有权记录。
- 建议：增加上传者、创建时间、绑定状态；上传频率/磁盘配额；仅允许归属一致的绑定。清理过期未引用文件需宽限期、先预览清单并按运维授权执行，不能直接批量删除头像目录。
- 验收：测试账号不能无限累积孤立文件、不能绑定另一账号的暂存文件；当前/历史仍被引用的头像不会被清理。

### F06：公开接口资源消耗边界不足

- 证据：`CaptchaController.generate/verify`、`LoginCaptchaService`、`RecruitmentController.register`、`RecruitmentService.register`；所查 Nginx 配置未配置 `limit_req`。
- 登录接口已有账号/IP 限流，但它不覆盖验证码生成和公开注册。公开注册已有一次性验证码及开放时间限制，**不是完全无防护注册**；仍未见独立注册尝试限额、验证码生成频率限制和全局资源预算。
- 注册涉及图片处理、密码哈希与数据库事务；匿名大量验证码请求不必先通过登录限流。实际抗压边界与外部 WAF 规则尚未测量。
- 建议：应用/网关组合限流，按 IP、行为、注册标识和全局容量分别控制；学校 NAT 环境需避免单 IP 误伤整个校园。监测验证码生成耗时、拒绝比例与队列长度。
- 验收：测试环境低上限验证返回 429/Retry-After；正常集体注册不被长期锁死。

### F07：参与人资格及 DTO 校验不足

- 证据：`FeeSubmitDTO` 的 `Map<String,Object> workInfo`、`ContributorDTO`；`FeeServiceImpl.submitFee` 的参与人循环；`FeeCalculationService.calculateSubsidy`；前端 `FeeSubmit.vue:613`。
- 后端校验提交人的部门权限，计算部分字段并拒绝部分非法值；但是没有在此调用链校验每个参与人是否有效，以及补贴人员是否具备该补贴类别要求的角色。前端的角色自动匹配不能代替后端规则。
- 外键只能保证人员存在，不能保证 `is_valid=1` 或符合补贴资格。不能把“允许手动排除人员”扩大成“可提交任何人员”。具体跨部门参与是否允许应由业务明确，不能一律禁止。
- workInfo 缺少类型化约束；贡献者数量、字符串长度等边界不完整。非法数字/日期可能入队后才以内部错误失败，增加无效队列负载。
- 建议：按作品类型拆 DTO/验证器，入队前做低成本校验、执行时复核动态权限；有效人员与补贴类别角色校验；明确合法的同人多角色规则；保留现有数据库唯一约束。
- 验收：合法角色可排除部分人员；无效人员、不符合补贴角色人员、超长字段/过多人员得到明确 400/403，不产生有效稿费记录。

### F08：分页接口实际全量加载

- 证据：`FeeServiceImpl.getFeeList:159`、`queryEditorialList:1475` 等五类查询、`resolveSubmitter:1622`。
- 先读取五类业务数据、逐条查询提交人，再过滤部门/平台/状态并在 Java 内存分页。即使请求 10 条，也可能读取全部历史任务及发出大量数据库查询。月份格式错误时只写警告并继续无月份过滤，可能意外扩大查询。
- 建议：把权限、类型、状态、月份条件下推数据库；使用数据库分页或统一查询视图；批量获取人员，避免 N+1；非法月份返回 400；大额导出设置数量/并发限制。
- 验收：测试库增加数据量后，单页 SQL 数量不随总记录数线性增长；不同角色仍只能获取授权数据，金额屏蔽不退化。

### F09：排队超时后无法继续跟踪原任务

- 证据：`src/api/fee.js:4` 每次生成新幂等键；`src/api/asyncTask.js` 默认等待 120 秒；`FeeSubmit.vue:700–726` 受理信息仅保存在局部变量。
- 超时不代表任务取消，但按钮重新可点；刷新页面/重试会丢失原 taskId/statusToken，产生新幂等键。与 F02/F03 叠加会放大误提交风险。
- 建议：按一次业务提交保存稳定幂等键与任务引用，区分“受理/处理中/完成/明确失败/结果未知”；提供继续查询和任务中心。任务令牌是凭证，应最小化保存并在完成/登出后清理。
- 验收：排队超过两分钟、断网恢复、刷新页面后仍能查询同一个任务；不能把等待超时显示成已经取消。

### F10：刷新请求可能挂起或发生标签页竞争

- 证据：`src/utils/request.js:21` 使用原始 `axios.post`，未设置 timeout，不继承 request 实例的 15000ms；`AuthTokenService.rotate` 实行一次性轮换与重放撤销。
- 一个不结束的刷新请求会让当前页所有等待刷新结果的请求持续等待。`refreshPromise` 只在当前标签页生效；两个标签页共享 refresh cookie，可能同时提交旧令牌，触发重放处置。后者需真实浏览器并发验证。
- 建议：刷新请求增加明确超时/取消；跨标签页协调刷新并同步登录态；区分真实重放与合法并发，不能直接取消后端的重放防护。
- 验收：模拟刷新不响应时页面能恢复操作并给出清晰提示；双标签页同时过期不会无故反复退出。

### F11：异步日志缺少来源关联

- 证据：`OperationLogServiceImpl.insertLog:88` 从 RequestContextHolder 取请求信息；`AsyncTaskEnvelope` 未携带 requestId/IP 等；`FeeServiceImpl.submitFee` 日志参数中 IP 为空。
- 工作线程没有原 HTTP 上下文，导致稿费创建等异步日志的请求 ID、路径、客户端、IP 不完整。当前创建日志也主要记录类型和人数，不能还原完整的受理来源。
- 建议：入队时构造经过校验的审计上下文，显式传递 requestId、taskId、操作者与必要来源信息；不传整份请求、Cookie、Authorization 或完整敏感资料。记录受理到完成的关联关系。
- 验收：从一条操作日志能关联原始请求和任务；资料字段继续脱敏；失败任务也能定位但不泄露凭证。

### F12：补贴人员排除结果在恢复草稿时丢失

- 证据：`FeeSubmit.vue:613` 从所有符合角色的用户重新生成列表；约 742–744 行先 `restoreFeeDraft()`，紧接着 `syncSubsidyContributors()`；删除函数只修改 contributors。
- 之前移除的人仍符合角色，恢复后又被自动加入。页面提示“已恢复草稿”，实际名单却改变，可能导致误发补贴。
- 建议：草稿保存“自动匹配名单+本次排除 ID”，或区分初次匹配和恢复模式；角色数据变化时明确提示用户确认。
- 验收：删除一人、等待草稿保存、刷新后该人仍排除；切换补贴类别的重置行为明确；全部删除时提示“请选择参与人员”，而不是错误暗示系统没有配置角色。

### F13：反向依赖与分层边界

- 没有在本次显式 import 图中发现循环；**存在分层耦合，不应混称为循环依赖或 Spring 启动死锁。**
- `AsyncTaskExecutionService` 注入具体 `security.UserDetailsServiceImpl`，业务执行依赖认证适配器实现；建议抽出身份/权限查询接口，由安全模块适配。
- `OperationLogServiceImpl` 依赖 `security.RequestTraceFilter` 的常量、ServletRequestAttributes 和 HTTP 请求上下文；这已经在异步场景产生 F11。
- `FeeService`/`FeeServiceImpl.exportFee` 使用 HttpServletResponse，业务服务负责 HTTP 响应写入。建议返回导出结果/流描述，响应头由 controller 或导出适配器处理。
- `AuthTokenService` 使用 JwtUtils/TokenPair 不自动构成错误：它本身就是认证基础设施的一部分。应按职责划分，不能为“消灭所有跨包 import”而机械重构。
- 验收：用 ArchUnit 等固化“业务不依赖 Web Filter/具体认证适配器”的规则；业务测试无需构造 HTTP response 或线程绑定 request。

### F14：部署不可从 Git 完整重现

- 证据：`docker-compose.yml` 初始化依赖 `sql/sja_system_db_202608131609.sql`，该快照在 `.gitignore` 中；当前 `deploy/nginx.https.conf.template`、镜像部署 compose 也被忽略且不在跟踪清单中。数据库迁移没有统一版本执行器。
- 不提交真实人员数据/密钥是正确的，但不能只保留含数据的本地快照作为初始化入口。另一台机器仅克隆代码就缺少必要的建库基线；已有数据卷不会因为更新 initdb 脚本自动完成升级。
- 建议：提交纯结构、脱敏字典基线和不含秘密的部署模板，秘密由变量/挂载提供；使用版本化迁移或显式升级清单，含校验与恢复说明。现有数据快照继续私下受控备份，不要为方便部署加入 Git。
- `sql.zip` 已被 Git 跟踪，本次只读检查其 6 个 SQL 成员，未检出 sys_user INSERT，不能据此指控已经泄露用户数据；但压缩包与散文件可能版本漂移，应明确唯一维护入口，任何删除另行审批。
- 验收：全新克隆在没有私人快照的条件下能初始化空系统；旧库按迁移升级且保留数据；生产凭证不进入 Git。全 Git 历史秘密扫描仍待完成。

### F15：测试通过但隔离和覆盖不足

- 证据：`SecurityBoundaryIntegrationTest:28–52` 只替换用户名/密码并 Mock 部分服务和 mapper；本次 Surefire XML 含数据库 `Access denied for user`，测试仍通过。
- 测试触发的失败审计会尝试访问真实数据源，而没有验证日志持久化成功。不能将该错误当作“预期隔离”忽略。应彻底 Mock 审计边界，或使用独立临时数据库测试完整链路，不依赖默认本机数据库。
- 前端 package.json 只有 dev/build/preview，无 test/lint/typecheck；pom 未配置架构测试、覆盖率阈值或静态分析门禁；Git 跟踪清单未发现 .github CI 工作流。
- 建议：补登录/权限、队列故障、重复计费、资料脱敏、导入导出、草稿恢复的回归测试；配置 lint、类型检查、依赖扫描与 CI；禁止测试回落到业务数据库 URL。
- 验收：无业务数据库/Redis 的开发机也能跑单测；集成测试使用专用临时服务；发生审计丢失时相关测试会失败，而不是仅打印日志。

### F16：生产默认配置及浏览器加固

- 证据：基础 `docker-compose.yml` Web 只发布 HTTP，显式传递 `SJA_REFRESH_COOKIE_SECURE` 默认 false；prod.yml 默认 true 会被该环境变量覆盖。`deploy/docker-compose.public.yml` 已显式 true，说明安全覆盖方案存在，但不能推断实际部署已使用。
- 基础 compose 未发布数据库/Redis端口，是正确的；网络名称 internal 只是名称，其 driver 为 bridge，没有 `internal: true`。这不等于数据库已暴露公网，是否开放仍需查服务器监听与安全组。
- 所查站点配置未见 CSP；HTTPS 模板静态 location 自己设置 add_header，需检查 HSTS 继承行为以及 API 与网关不同 HSTS 值。不要直接上线未经适配的严格 CSP 导致前端不可用。
- 建议：公网生产启动前检查 HTTPS origin、secure cookie、独立任务密钥和可信代理边界，缺配置时明确拒绝或预检失败；CSP 先 report-only；仅开放 Web 必需入口。检查 Cloudflare/其他代理是否覆盖并可信传递真实客户端 IP，防止全站共享限流桶或伪造来源。
- 验收：从外部验证 HTTP 跳 HTTPS、Set-Cookie Secure/HttpOnly/SameSite、CORS 非白名单拒绝、头像 no-store、3306/6379/后端端口不可直连；不同客户端限流相互独立。不能只查看源码声明。

### F17：UTC 默认日期与本地日期不一致

- 证据：`FeeSubmit.vue:398,418` 使用 `new Date().toISOString().slice(...)`。
- 中国时区凌晨 00:00–07:59，UTC 日期仍可能是前一天；每月一日凌晨，补贴月份可能默认上月。
- 建议：以明确业务时区计算日期月份，而不是对 UTC 字符串截取。
- 验收：Asia/Shanghai 下 9 月 1 日 00:30，默认日期为 9 月 1 日，月份为 9 月；跨年同样验证。

### F18：未发布与月份筛选组合没有清楚定义

- 证据：`normalizeUnpublishedPublishDate` 清除未发布日期；`queryEditorialList` 等按 publish_date 范围过滤；随后才应用 UNPUBLISHED 条件。
- 用户选定某个月再选未发布，通常得到空结果，因为未发布记录没有 publish_date。不是数据必然丢失，而是筛选口径不一致。
- 建议：明确月份表示发布日期、提交日期还是归属月份；未发布时禁用不适用的月份并说明，或增加独立的归属月份。不要悄悄改用提交日期而不改标签。
- 验收：组合筛选结果与页面说明一致，空状态说明筛选原因并支持一键清除。

### F19：首包、刷新与错误反馈体验

- 证据：本次构建主 JS gzip 386.29 kB；`src/utils/request.js` blob 分支与业务错误分支；`GlobalExceptionHandler` 的兜底异常处理。
- 大包是性能信号，不是已测得手机卡顿。优先实测低端设备/弱网，再评估组件按需导入和合理拆包，不能只调高警告阈值。
- Blob 导出失败时错误内容可能不能直接读成 message，页面只显示通用网络错误；业务 code 非 200 分支未遵守 skipGlobalError，局部错误提示可能重复。
- 非法 JSON/部分参数转换没有专门异常映射，可能进入 500 兜底。对用户输入问题应返回可理解的 400；数据库内部详情继续只保留在服务端。
- 验收：无权限导出、网络超时、非法字段、任务仍在执行分别显示准确提示；错误提示不重复；键盘焦点、按钮加载状态和移动布局需另做浏览器验收。

### F20：规范与维护成本

- 证据：FeeServiceImpl 1831 行、UserServiceImpl 976 行；FeeAudit.vue 1170 行、FeeSubmit.vue 997 行、UserManagement.vue 999 行。

- 建议：按职责拆分但不一次性重写；统一角色/作品类型常量与权限策略；抽出共享验证器和导出元数据；lint/格式化/注释规则自动检查。规范化历史注释时不要编造原修改时间，可追加真实整改时间。
- 验收：新增规则有唯一明确入口；大模块拆分有回归保护；新增代码注释满足约定，构建与 lint 在 CI 自动执行。

## 4. 待进一步验证的风险（不冒充已复现漏洞）

1. **Redis 断线后的订阅恢复**：AsyncTaskQueueConfiguration 只注册 errorHandler 并启动一次；AsyncTaskWorker 恢复的是 pending 消息。需断开/恢复 Redis，验证未读消息继续被消费，不能仅确认旧 pending 被接管。当前未完成该故障试验。
2. **任务可见性与锁超时**：锁无续租，pending 恢复固定扫描前 100 条。长任务、工作线程排队和多消费者条件下需验证无饥饿、无重复执行。数据库同 taskId 完成标记已有保护，应保留。
3. **多租户/对象级权限**：真实管理员、部长、普通用户、访客逐项核验查看/修改/审核/导出其他人员、其他部门的数据。部长跨部门查看在代码中有明确设计注释，不能未经业务确认直接判为越权。
4. **头像对象级策略**：已登录用户可读取已绑定头像，读取接口没有“仅本人”的限制。若业务要求仅本人或人员管理员可读，需要增加对象授权；不能把“禁止匿名”直接等同“禁止所有其他登录用户”。
5. **文档解析资源隔离**：UserImportService 已有文件大小和行数上限，但压缩文件解析内存不等于原文件大小。在测试环境验证超大解压比、超多条目与超时隔离，不对生产投递资源耗尽样本。[POI 官方安全处理建议](https://poi.apache.org/security.html)
6. **数据与秘密生命周期**：核验数据库磁盘/备份访问控制、敏感字段加密需求、导出文件权限和保留期；刷新令牌历史、审计表和异步完成表需要容量/清理策略。本次没有读取真实密码、令牌或导出用户隐私作为证据。
7. **完整供应链检查**：Java 全依赖、容器 OS/JDK/Nginx、Git 全历史秘密扫描和许可证审查尚未完成。npm 0 漏洞不覆盖这些部分。
8. **财务及 Excel 业务验收**：以脱敏样本比较六种表的列、合并、特殊节点、倍率、文件名、合计与权限；多人分摊向上取整是当前代码明确选择，是否允许总额增加必须由财务口径确认，而非擅自判定或修改。

## 5. 已有保护，整改时不能退化

- Spring Security 默认认证、方法级权限、强制改密过滤器；头像已不在匿名放行范围。
- 登录 Redis 账号/IP 节流、失败锁定、验证码二次消费、Retry-After；Redis 故障时拒绝登录而不是绕过保护。
- JWT 校验用户状态及版本；refresh token 哈希存储、轮换和重放处置；Cookie HttpOnly/SameSite。
- CORS 配置拒绝空值与通配符；生产 API 文档禁用配置存在。
- 图片真实解码、像素限制、重编码、路径限制；未绑定文件不能直接作为公开头像读出。
- 异步 payload AES-GCM 加密、任务状态令牌常量时间比较、执行前重新读取权限；不能因优化轮询改成任务 ID 即可查所有状态。
- 稿费在后端重新计算，金额权限在后端执行；数据库已有部分唯一约束和外键；日志有脱敏处理。
