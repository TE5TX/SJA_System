# 人员批量导入开发方案

202609181030 - 完成了十列 XLSX 人员批量导入与团内职务预设的开发方案。

## 1. 目标与范围

在“系统管理”下新增独立的“人员批量导入”页。管理员、主席、秘书长可在导入前为本批人员设定统一的团内职务，上传 XLSX，预览逐行校验结果，确认后导入有效行。无效行或单行写入失败时跳过该行；结束后弹窗展示成功、跳过数量和原因。原有人员信息、批量注册及其他业务功能保持可用。

本次只新增人员，不覆盖或更新已存在人员。每行只要求填写姓名、学号、身份证号码；其余七个字段允许为空。学号同时作为登录账号，初始密码统一为 `asdf123456`，沿用 `UserService.createUser` 的现有规则，并要求首次登录修改。页面在导入前明确告知操作人初始密码规则；不得在日志、失败报告或浏览器持久存储中输出每个人的密码。

## 2. XLSX 格式与字段映射

第一行是表头，读取第一个工作表。要求以下十个表头各出现一次，但不要求顺序固定；其他列可忽略并在预览中提示。表头匹配时去除首尾空白、BOM 和全角空格；不对未知列名进行模糊猜测。缺少或重复必需表头时，整个文件报错，不执行导入。

| XLSX 表头 | 系统字段 | 行内要求 |
| --- | --- | --- |
| 姓名 | `sys_user.real_name` | 必填，最长 50 字符 |
| 学号 | `sys_user.student_no`、`username` | 必填，1–20 位数字；作为唯一账号 |
| 二级学院 | `sys_user.college` | 可空，最长 100 字符 |
| 年级专业班级 | `sys_user.class_name` | 可空，最长 50 字符 |
| 手机号码 | `sys_user.phone` | 可空；非空时必须为系统允许的手机号格式且不能重复 |
| 身份证号码 | `sys_user.id_card` | 必填；按系统格式校验、末尾 `x` 规范为 `X`，且不能重复 |
| 宿舍地址 | `sys_user.dorm_address` | 可空，最长 100 字符 |
| 团内部门 | `sys_user_dept` | 可空；非空时精确匹配启用的部门名称，允许用“、”分隔多个部门并去重 |
| 正式部员/留任部员 | `sys_user_role` 中的成员身份 | 可空；非空时只接受“正式部员”或“留任部员”，分别匹配现有角色，不写入备注来替代角色 |
| 银行卡号 | `sys_user.bank_card` | 可空；非空时必须为 10–30 位数字 |

模板将学号、手机号、身份证号码、银行卡号四列设置为文本格式。解析时保留单元格的原始文本，不转换成浮点数或科学计数法；这些列若使用数值单元格，标记该行无效并提示将列设为文本后重新填写，因为 Excel 可能已丢失长数字精度。完全空白的行不计入总数。记录原始 Excel 行号，便于定位错误。

## 3. 导入前设置团内职务

页面第一步为必选的“本批团内职务”单选框，先选职务再上传文件。候选职务从系统当前启用的角色查询，不在前端写死角色 ID；仅列出当前操作人有权分配的职务，不提供管理员、老师等不适合批量授予的高权限角色。可选择“正式部员”或“留任部员”作为整批统一职务；不能留空或选择虚构的角色。

每位新用户最终角色为：`所选团内职务 + 该行非空的正式/留任成员身份`，相同角色去重。若统一职务为“正式部员”而某行填了“留任部员”（或反之），该行标记为冲突并跳过，不能同时赋予相互排斥的成员身份。行内成员身份留空时只赋予统一职务。后端在预览和确认时都重新校验角色是否仍启用、操作者是否有权分配；前端隐藏选项不能代替后端授权。非空部门和成员身份也在确认时重新校验。

预览界面同时展示统一职务、每行部门与成员身份；可空字段为空时显示“未填写”。确认弹窗明确列出“将创建多少个账号”、选定的职务及“学号为账号、初始密码为 `asdf123456`，首次登录须修改”。沿用现有的当前密码确认机制。

## 4. 页面交互

1. 在系统管理菜单增加“人员批量导入”，路由仅允许有批量导入权限的用户访问。页面提供模板下载、统一职务选择、上传控件和格式说明。
2. 上传后先调用预览接口；显示总行数、有效数、预计跳过数及逐行原因。表格可按“全部/可导入/将跳过”筛选。包含无效行时仍允许确认导入有效行，但必须显示明确的跳过数量。
3. 用户输入当前密码并确认。按钮处于执行中时禁止重复提交或切换文件。
4. 服务端处理完成后弹出结果对话框：总数、成功数、跳过数、每条失败行的 Excel 行号和简洁原因；可下载失败明细 XLSX。下载内容只保留定位必需字段（如行号、姓名、学号及原因），不导出身份证号、手机号、银行卡号。
5. 成功数大于零时刷新人员信息页数据；结果对话框关闭后仍可重新导入修正过的失败行。接口级错误（例如文件损坏、表头错误、权限不足）与行级错误分开显示。

## 5. 后端流程与事务边界

### 5.1 预览

在现有 `UserImportService` 中复用文件大小、最多行数、操作者校验、Redis 一次性预览令牌等机制；为十列表格增加独立解析策略，避免改变现有两列表格导入行为。按列名建立 `字段 -> 列序号` 映射，再读取数据。只对姓名、学号、身份证号码做非空校验；其余字段为空时跳过对应格式与匹配校验，非空时才校验合法性。校验文件内重复，以及数据库中已存在的学号、手机号和身份证号；手机号只对非空值检查重复。对于重复记录，保留第一条通过校验的候选行，后续相同记录标记跳过；预览响应携带每行状态与原因。

预览成功后，仅把可导入候选行、所选职务和必要的部门/身份映射写入短期 Redis 快照；令牌与操作人绑定、有有效期、只能消费一次。快照含个人信息，沿用短期 TTL，禁止写入常规日志。若有效行数为零，不发放确认令牌。

### 5.2 确认与逐行写入

确认接口校验当前密码、消费一次性令牌，并重新检查角色授权、部门状态和待导入账号是否已被其他操作创建。每一行进入独立事务，调用现有 `UserService.createUser` 创建用户及角色/部门关联。一个用户的写入失败时，该行事务整体回滚，但此前成功行不回滚，后续行继续执行。行级事务应放在独立 Spring Bean 的公开方法中，避免同类内部调用导致事务注解失效；外层批处理方法不套全局事务。

并发插入导致的唯一键冲突作为该行失败记录，不导致整批中止。仅捕获可归因于单行数据或写入的异常；数据库整体不可用等基础设施故障应停止处理并返回已完成数量、未处理数量与中止原因，不能把所有剩余行伪装成“数据错误”。成功/失败数量与写入事实保持一致。通过已有操作日志记录操作人、批次、职务、成功数和跳过数，不记录完整敏感信息。

返回结构建议包括 `totalCount`、`importedCount`、`skippedCount`、`unprocessedCount`、`failures[{rowNumber, realName, studentNo, reason}]` 和 `aborted`。不返回完整身份证号、手机号或银行卡号。

## 7. 测试与验收

- 乱序十列、附加列、空白行能够正确解析；缺失/重复表头和文件类型、大小、行数超限得到明确提示。
- 仅姓名、学号、身份证号码必填；其余七列值留空时仍能导入。统一职务正确写入；行内正式/留任身份非空时正确叠加，同类去重、冲突跳过；无权分配、已禁用角色或非空但不存在的部门在后端被拒绝。
- 学号、非空手机号、身份证号在文件内或数据库中重复时只跳过对应行；手机号、身份证号、银行卡号格式错误时给出行号及原因。学号作为账号，初始密码 `asdf123456`，首次登录须修改。
- 中间一行写入失败时，前后有效行成功，失败行的用户及关联记录均未残留；重复点击确认不能二次导入。
- 正常结束时弹窗满足 `总数 = 成功数 + 跳过数`；基础设施故障中止时满足 `总数 = 成功数 + 跳过数 + 未处理数`。成功数与数据库真实新增人数一致；失败明细不包含完整敏感字段。
- 原有两列批量注册继续通过回归测试；前后端构建与相关接口测试通过。
